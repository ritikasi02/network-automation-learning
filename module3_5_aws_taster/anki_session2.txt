SCENARIO (lab-hello, AWS Lambda console): the starter code is "def lambda_handler(event, context): return {'statusCode': 200, 'body': json.dumps('Hello from Lambda!')}". You press Test with the event {"file": "beach.jpg"}. The body still says Hello from Lambda, not beach.jpg. Your S3 bucket holds a PDF, no image. Did the function read your file or your event, and why is beach.jpg irrelevant here?	Neither your file nor your event was used. Test only hands the typed JSON to the function as "event" and shows what it returns; S3 is never contacted. The starter code never reads event, so it returns the same fixed string no matter what you type. beach.jpg was a made-up label on a pretend doorbell, not a filename AWS looks up. The PDF in S3 is unrelated because this function does not touch S3.
What is AWS Lambda in one sentence, and name two jobs it is wrong for?	Lambda is a function AWS runs when an event arrives, then stops; you are billed only for the seconds it runs, and you never patch a server. It is wrong for a program that must stay up continuously (use a long-running server / EC2) and for work longer than its 15-minute limit. "Cold start" is the slower first run after idle while AWS builds the environment; it is not a code bug.
SCENARIO (lab-hello): the code does "body: json.dumps(event['file'])" and you send the event {"name": "beach.jpg"}. The Response panel turns red with errorType KeyError, errorMessage 'file', and no statusCode anywhere. You expected statusCode 200 regardless. Why is there no 200?	A return is one statement: Python must finish building the whole dict before returning it. Building it evaluates event['file'], which raises KeyError because there is no 'file' key, so the return never completes and no statusCode is ever produced. The run is marked failed because the function raised, not because of any number. On a plain Test or event trigger, AWS does not read statusCode at all; success means the function returned, failure means it raised.
SCENARIO (lab-hello): a missing key crashed the function. You must decide between returning a 400 that says the key is missing, or defaulting the filename to a placeholder like "unknown.jpg" so the function keeps going. Which is correct and why?	Return the 400. Defaulting to a made-up value lets the function keep working on data that is not real, so in a live app it would resize, email, or report the wrong thing while reporting success and hiding the problem. A 400 fails loud and early and tells the caller to fix their request. Rule: validate input at the door, fail clearly, never substitute a fake value to avoid an error. Read the key with event.get('file') (returns None instead of raising) so you choose what happens, not Python.
SCENARIO (lab-hello): line 4 is "filename: event.get('name')" (a colon). Running it gives UnboundLocalError: cannot access local variable 'filename', pointing at line 5 "if filename is None:". What is wrong and what is the fix?	A colon makes "filename: ..." a type annotation, not an assignment, so filename is never given a value and line 5 cannot read it. The fix is the assignment operator "=": filename = event.get('name'). Lesson: the traceback names the exact variable and line, so read it top-down, then look there. UnboundLocalError means "this local name was never assigned", different from KeyError (a dict key is missing).
Why put print(json.dumps(event)) as the FIRST line of a Lambda handler, and what happens if it is placed after the return?	First-line logging captures the input before any logic that might crash or return early, so even if the function blows up later you can see what came in. A print placed after a return is dead code: return exits the function immediately, so it never runs (this looks exactly like "no print line appears in the log"). Rule of thumb: log the input at the top, log the result just before each return, because the CloudWatch log is the only witness to a run no human watched.
SCENARIO: lab-hello works on the Test button but you want a browser to call it. You turn on a Function URL with Auth type NONE. What did that create, and what is the security caveat?	A Function URL is a dedicated public HTTPS address bound to that one function; hitting it invokes the function, with the HTTP request delivered as the event. Auth type NONE means anyone on the internet with the URL can invoke it. That is acceptable only because this function just echoes a filename and touches nothing. Never use NONE for a function that reads data or spends money. Function URLs suit "one function, one URL"; API Gateway is the choice for a full API (routing, auth, rate limiting, custom domain).
SCENARIO (lab-hello Function URL): you load the URL with no query string. The browser shows your 400 "file does not exist", not an error page, and the HTTP status really is 400. Is a 400 the same as "the page failed to load", and who chose that 400?	No. The page loaded fine; the exchange succeeded. The status is a separate verdict the server chooses and the browser only reads. Your function ran successfully and deliberately returned 400 to say "bad request". If the function had instead crashed (raised), your code would set no status and AWS's front door would return 502/500 on its own. A status is always chosen by whoever answered; the browser never invents it. With a Function URL, AWS reads your statusCode and makes it the real HTTP status, so now your 200/400 finally mean something to a caller.
SCENARIO (lab-hello Function URL): code reads event.get('name') and the browser request ...on.aws/?name=beach.jpg still returns 400. The logged event has top-level keys version, routeKey, rawPath, rawQueryString, headers, queryStringParameters, requestContext, isBase64Encoded, and "queryStringParameters": {"name": "beach.jpg"}. Where is the code looking vs where the value is?	event.get('name') searches only the top-level keys (the outermost keys of the event dict). There is no 'name' at that level, so it returns None and you get the 400. The value lives one level down, inside the queryStringParameters drawer: event['queryStringParameters']['name']. Lesson: the event shape is set by the trigger. A Function URL (payload v2.0) nests query params under queryStringParameters; a Test event you type by hand puts keys wherever you typed them; an S3 trigger nests the key at event['Records'][0]['s3']['object']['key']. Read the shape your actual trigger sends.
SCENARIO (lab-hello): to read a Function URL query param safely the code is "params = event.get('queryStringParameters'); if params is None: params = {}; filename = params.get('name')". Why guard params against None instead of writing event['queryStringParameters']['name'] in one line?	When the URL has no query string, AWS sends queryStringParameters as null (Python None), and reading a key off None raises a crash just like the earlier KeyError. The one-line chained lookup crashes if either level is missing. Reading each level with .get plus the None->{} guard turns "no query string" into your clean 400 instead of a traceback. 'params' is just a chosen variable name holding the drawer; the string passed to event.get is the real top-level key "queryStringParameters".
SCENARIO (lab-hello): the handler ends with "if filename is None: return {400...} return {200...}" where BOTH returns are indented inside the if. ?name=beach.jpg returns null; the plain URL returns 400. Why null, and what is the fix?	Both returns are inside the if block. When name is present, filename is not None, so the whole if is skipped, there is no return after it, and a Python function that ends without returning gives back None -> shown as null. The 200 return is also dead code: it sits right after return 400 in the same block and can never be reached. Fix: dedent the 200 return so it aligns with "if", making it a sibling of the if that runs when the if did not. In Python, indentation IS the block structure.
