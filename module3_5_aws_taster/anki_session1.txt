SCENARIO: a teammate creates an S3 bucket and leaves it readable by anyone on the internet. Config backups land in it. They say AWS is responsible for security, so the public bucket is Amazon's fault. Which side of the shared responsibility model failed, and what has to change?	The customer side failed. AWS runs the storage service. The bucket's access setting is the customer's configuration, the same class of mistake as giving a machine more privileges than its job. Change the bucket so it is not public, and give each workload only the actions it needs. AWS secures the platform. You secure identity, network rules, and data.
You sign up with GitHub on Sign up for AWS (new). The console home URL contains region=ap-southeast-2. The Budgets page URL contains us-east-1. Which region will a later Lambda actually be created in, and why are both URLs telling the truth?	The Lambda is created in ap-southeast-2 (Asia Pacific, Sydney). India on this signup is assigned Sydney, and this signup cannot move the project to N. Virginia. The Budgets console is hosted in us-east-1 because a budget watches money for the whole account. It is not a resource that lives in Virginia. Stay in Sydney for every Lambda and bucket.
The account is on the free plan with $100 credits and about 183 days left. A monthly cost budget named My Monthly Cost Budget is set to $10 and shows $0 used. Does that budget stop a resource from running, and what else do you watch so the account does not end early?	The budget only emails you. It does not stop the resource. On the free plan, credits cover usage, so the amount owed can stay $0 while credits shrink. Watch Credits remaining and days remaining. The plan ends when the credits run out or the trial days end, whichever comes first, and then the account closes unless you upgrade.
SCENARIO: the Mac already has a default AWS profile with region ap-south-1. For the new project you run aws login --profile hello-aws and set that profile's region to ap-southeast-2. Why is the named profile required, and why do you not run aws configure and paste an AKIA access key?	Without --profile hello-aws, the CLI uses default and talks to Mumbai, which is not this project. hello-aws is the Sydney session. aws login opens a browser, you approve the GitHub login, and the CLI keeps a temporary session for about 12 hours. An AKIA key is a long-lived secret, the same kind of leak as a Meraki API key in git. This signup's owner is the GitHub login. Do not create a second user or a key pair for the lab.
sts get-caller-identity --profile hello-aws prints an Arn whose middle looks like assumed-role/AccountFullAccessRole/SESSION. What did you assume, and why is that acceptable for an empty lab but the wrong identity for a Lambda that only needs one bucket?	You assumed the role AccountFullAccessRole for this session. The role name is the policy: full access to the project, the cloud version of permit ip any any. Fine while you are the human setting up an empty lab. A Lambda must not run as that role. When a function needs S3, it gets its own role that allows only that bucket. Your login is the person. The function's role is the program.
