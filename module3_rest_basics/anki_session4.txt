Why wrap the CML login script in a class instead of copying requests.post and requests.get for every new endpoint?	login() and get_labs() were repeating the same setup: base URL, timeout=10, verify=False, and the Bearer header. A class holds that shared setup as state (self.base_url, self.token, self.session) and exposes each endpoint as a method. Adding get_nodes later reuses the session instead of pasting the header again. Rule: when many operations share the same setup and the same data, that data wants to live on an object and those operations want to be its methods.
SCENARIO (cml_client.py): class CmlClient has def __init__(self, base_url, username, password) that sets self.base_url = base_url and self.token = None. The bottom of the file has if __name__ == '__main__': which reads os.environ and does client = CmlClient(base, user, pw). What runs when, and why does the class NOT read os.environ itself?	__init__ runs automatically every time you write CmlClient(...). Its job is to store the starting state on the object. The if __name__ == '__main__' block runs only when you execute python3 cml_client.py; it is the caller that reads CML_URL, CML_USER, CML_PASS and passes them in. The class waits to be handed values so the same client can be built from env vars, a test, or another file. That split is separation of concerns: the class talks to CML; the caller decides where the config came from.
What is the difference between __init__ and if __name__ == '__main__'?	__init__ is a method inside the class. It runs every time an object is created and sets self.* state. if __name__ == '__main__' is a block at the bottom of the file. It runs only when that file is executed directly as a script, not when another file imports the class. One builds an object. The other is the script entry point. You use both in the same file: the guard creates a CmlClient and calls login() and get_labs().
SCENARIO: CML_login.py has no if __name__ == '__main__' guard. Its top level reads env vars, POSTs to /authenticate, and prints. Why is from CML_login import url a bad way to reuse the URL, and what should you import instead?	Importing a file runs the whole file first. Importing CML_login.py would fire a live login and print output just to borrow a variable. Those variables are not the source of truth anyway; they were read from os.environ. Put reusable definitions (the class) at the top with no side effects, and put 'actually log in and print' under the __main__ guard. Then another module can from cml_client import CmlClient and get only the class.
SCENARIO (cml_client.py): __init__ sets self.token = None. __main__ prints client.token, then calls client.login(), then prints len(client.token) and sees 279. Why did the first print show None even though login works?	Python runs top to bottom. The first print happens BEFORE client.login(), so it shows the value __init__ stored: None, meaning 'not logged in yet'. login() then does self.token = response.json(), so the token exists only after that line. len(client.token) == 279 proves a real token is on the object. Print the length, never the token: a Bearer token is a live credential.
SCENARIO (cml_client.py login): after self.session.post(...) the method calls response.raise_for_status() before self.token = response.json(). CML once answered 403 Forbidden. What does raise_for_status do, and why is that better than if response.status_code == 200: print('login ok')?	raise_for_status() does nothing on 2xx and raises requests.exceptions.HTTPError on 4xx/5xx. A 403 stopped the method immediately, so self.token stayed None instead of the script continuing as if login had worked. Fail fast: a method that cannot log in should crash at the login line, not fail mysteriously on a later GET. The caller can catch HTTPError if it wants a friendly message.
SCENARIO (cml_client.py): login() ends with self.session.headers.update({'Authorization': f'Bearer {self.token}'}). get_labs() is only response = self.session.get(self._url('labs'), timeout=10) with no headers= argument, and it still returns the lab UUIDs. Where did the token go?	self.session is one requests.Session object created in __init__ and shared by every method. login() writes the Bearer header into that session's headers dict. self.session.get automatically stamps the session's stored headers onto the outgoing request. get_labs() never rebuilds the header because it uses the same session object login() already updated. Bare requests.get would forget the header; a Session remembers it. That is persistent auth: log in once, every later call carries the token.
What does a leading underscore mean on def _url(self, path), and what problem does that helper remove?	A leading underscore is a convention: this method is for the class's own use, not part of the public 'things callers should call' surface. _url returns f'{self.base_url}/api/v0/{path}', so login, get_labs, and get_lab stop repeating the host and the /api/v0/ prefix. Change the API version in one place. Callers still use login(), get_labs(), and get_lab(); they do not call _url themselves.
SCENARIO (cml_client.py): get_labs() returns a list of UUID strings. The loop is for lab_id in labs: detail = client.get_lab(lab_id). The first attempt print(detail['title'], detail['status']) raised KeyError: 'title' even though the GET succeeded. Why is detail a dict, and why was the key wrong?	lab_id is only the UUID string; it returns nothing. get_lab sends GET /api/v0/labs/{id}. CML's body for that URL is a JSON object, so response.json() is a Python dict. get_labs returns a JSON array, so that one is a list. KeyError after a successful call (raise_for_status did not fire) means the dict arrived but that key is not in it. Live CML uses lab_title and state, not title and status. sample_responses/labs.json used simpler names and is not the live contract. Print list(detail.keys()) before guessing field names.
Why should get_labs and get_lab return response.json() instead of printing inside the method?	print sends text to the screen and throws the value away. return hands the list or dict back to the caller, who can print it, filter it, or pass it to the next call. In __main__, labs = client.get_labs() only works because get_labs returned the list. A reusable client is a library: methods do the HTTP work and give data back; the caller decides what to do with it.
