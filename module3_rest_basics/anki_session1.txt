What is the difference between asking a device for interface data over SSH (Module 2) versus over a REST API (Module 3), in one mental model?	Same job (get structured facts about the device), different door. SSH: your Python opens a CLI session and send_command('show ip int brief') scrapes a blob of text designed for human eyes. REST: your Python sends an HTTP request (a method + a URL) and gets JSON back — already fields you can look up. One-liner: SSH scrapes a human interface; REST consumes a machine interface.
SCENARIO (first_call.py): the script does response = requests.get('https://jsonplaceholder.typicode.com/users', timeout=10) then prints response.status_code and later uses response.json(). What is response, what does 200 mean, and why look at the status BEFORE the body?	response is a Response object — the whole reply package (status, headers, body), not the JSON itself. 200 means the GET succeeded (2xx = success). You look at status first because the body can be JSON even on failure (a 401 can still be {'error': 'unauthorized'}). Treating any JSON as success hides auth and 'not found' failures. Rule: status first, then parse the body.
SCENARIO (first_call.py, line that failed): response = requests.get(url=https//jsonplaceholder.typicode.com/users, timeout=10) raised NameError: name 'https' is not defined. Why, and what is the fix?	Without quotes, Python treats https as a VARIABLE NAME, not as text. That name was never assigned, so NameError. The earlier SyntaxError on https://... (no quotes) was the same class of bug: the colon looked like syntax. Fix: the URL is a string — wrap the FULL address, including https://, in quotes. Same lesson as os.environ[NET_USER] vs os.environ['NET_USER'] in Module 2: a name that is data must be quoted.
SCENARIO (first_call.py): after adding quotes, the line was requests.get('https://https//jsonplaceholder.typicode.com/users?', timeout=10) and the traceback said Failed to resolve 'https' / host='https' (ConnectionError / NameResolutionError). What went wrong, and which line in a long HTTP traceback do you read first?	A URL is scheme://host/path. https:// is the scheme and must appear ONCE; the next piece must be the hostname (jsonplaceholder.typicode.com). Doubling it (https://https//...) made requests treat the word https as the host. DNS then tried to resolve a computer named https and failed — that is a NETWORK/address error, not a Python syntax error. In a long urllib3/retry traceback, find host= and Failed to resolve — that is what you actually dialed. Extra ? at the end starts an empty query string; drop it unless you have parameters.
Why pass timeout=10 to requests.get, and what happens if you omit it?	timeout=10 means 'give up after 10 seconds if the server does not answer.' Without it, a dead or hung API can block your script forever — a stuck nightly job, not a clean failure. Always set timeout on HTTP calls (AUTOCOR 1.6). This is the HTTP cousin of NetmikoTimeoutException: you decide how long 'no answer' is allowed to last.
SCENARIO (first_call.py): user = response.json() then for entry in user: print(entry['name']). What type is user, what type is entry, and why is the loop not written for entry in user['users']?	This API's JSON body is a JSON array, so .json() returns a Python LIST of dicts. user (better named users) IS the list; there is no outer wrapper key. entry is one dict (one user). for entry in user walks that list directly. for entry in user['users'] would be correct only if the body were {'users': [ ... ]} — a dict with a 'users' key. Draw the outer type first: [ means list, { means dict. Wrong outer type -> TypeError or KeyError.
Why do you write entry['name'] to read a field, not entry{'name'} or {}, even though name lives inside a dictionary?	{} CREATES a dict (person = {'name': 'Leanne'}). [] LOOKS UP a field that already exists (person['name']). After .json(), the dicts already exist; you are reading, not building. entry{'name'} is invalid syntax. The same [] is used on lists (user[0] = position) and dicts (entry['name'] = key) — meaning depends on what is on the left. Rule: curly braces make a dict; square brackets get (or set) one item.
SCENARIO (first_call.py): city is not next to name. The working access is entry['address']['city']. Why two pairs of brackets, and what error do you get if you write entry['city'] instead?	In each user dict, address is itself a dict: { 'name': '...', 'address': { 'city': 'Gwenborough', ... } }. First ['address'] opens the inner dict; second ['city'] reads the field. entry['city'] looks for a TOP-LEVEL key city, which is not there, so KeyError: 'city'. That is a Python data-shape error, not an HTTP failure — status was already 200. Rule: draw the path from the outer key to the field before you write the lookup. Nested JSON is normal for APIs (labs -> nodes -> interfaces).
How do you tell a bad URL/path (HTTP) from a bad JSON key (Python) when an API script fails?	If requests raises ConnectionError / NameResolutionError, or status_code is 4xx/5xx, the PROBLEM IS THE REQUEST (host, path, auth, server). If status is 200 and then you get KeyError or TypeError while walking .json(), the HTTP call worked — YOUR PATH THROUGH THE DATA is wrong (list vs dict, missing key, forgot a nesting level). Split: network/HTTP first, then data shape. Same diagnostic habit as Module 2 timeout (reachability) vs auth (credentials).
Why did pip install -r module3_rest_basics/requirements.txt fail with No such file or directory when the terminal prompt showed module2_ssh_automation?	The path was RELATIVE to the current working directory (the folder in the prompt). From inside module2_ssh_automation, bash looked for module2_ssh_automation/module3_rest_basics/requirements.txt, which does not exist — Module 3 is a SIBLING, not a child. cd module3_rest_basics failed for the same reason. Fix: cd to the repo root first, or cd .. from Module 2. Rule: a path that does not start with / starts from the room you are standing in.
