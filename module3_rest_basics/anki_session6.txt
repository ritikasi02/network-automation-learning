SCENARIO (cml_client.py): the for loop catches requests.exceptions.HTTPError and branches on status. get_lab uses timeout=10. CML at 10.104.55.88 does not answer, and the traceback says ConnectTimeout with connect timeout=10 on the GET. Does the HTTPError handler run? What runs instead if you added except requests.exceptions.Timeout beside it?	The HTTPError handler does not run. session.get raises ConnectTimeout before raise_for_status(), so there is no HTTP response and no status code. Timeout is a different exception. A sibling except requests.exceptions.Timeout prints 'timeout, skipped' and the for continues. login() stays outside that try: if the controller is unreachable at login, the script should stop because there is no token and no lab list. ConnectTimeout means TCP never connected (host down, VPN, wrong IP). ReadTimeout means the connection opened and the body never arrived. requests.exceptions.Timeout is the parent of both.
Why must except Timeout sit beside except HTTPError, and not inside the HTTPError handler? What happens to a timeout raised by the second get_lab call inside the 401 branch?	Python picks the first matching except for the try, in order. Timeout is not a subclass of HTTPError, so it needs its own except on that same try. Once Python has entered the HTTPError handler, a new exception inside that handler is not offered to the sibling except Timeout. The retry get_lab inside the 401 branch can still kill the script on a timeout. Sibling handlers only apply to the original try.
SCENARIO (cml_client.py): a GET returns 429. The code only has if status in (400, 404), elif status == 401, else: print('request failed'). Which branch runs, and why is break the wrong fix?	429 is an HTTPError, and it matches neither 400/404 nor 401, so it hits else. break would abandon every later lab, and those labs are still valid. 429 means the pace is too fast, not that the job should stop. Read Retry-After (seconds) from error.response.headers.get('Retry-After'); if it is missing, wait 2 seconds. time.sleep(wait), then retry that same lab_id once inside its own try. Then the for continues. Immediate retry is what the server just refused. AUTOCOR 1.6 calls this rate-limit handling.
What is the difference between 400 and 404 on GET /api/v0/labs/{id}, using the call that returned 400 for 'this-lab-does-not-exist'?	400 Bad Request: the path segment is not a UUID, so CML rejects the shape and does not search. The real call was GET .../labs/this-lab-does-not-exist. 404 Not Found: the segment is a real UUID, CML searches, and no lab has that id (for example .../labs/00000000-0000-4000-8000-000000000099). Both are 4xx (your request). Neither is fixed by logging in again, so both belong in the skip branch. The printed status still matters: 400 means the script built a bad id; 404 means a well-formed id and the lab is gone.
In an interview, how do you group REST client failures instead of listing every status code?	Group by the next action. 400/404: skip this item, the id is bad or gone. 401: login once and retry this item once (persistent auth / expired token). 429: sleep using Retry-After, then retry once (rate limit). Timeout or connection error: no HTTP body; skip or retry with backoff, and do not read status_code. 5xx and anything else: report the status; do not pretend it is a bad id. Keep the try inside the loop so one failure does not drop the rest. AUTOCOR 1.6: pagination, auth, rate limiting, error handling, persistent auth.
