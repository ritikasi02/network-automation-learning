Why does REST being STATELESS force you to send a token on every single request, when SSH (Module 2) let you log in once and stay logged in?	SSH opens a session on an open channel that HOLDS your identity for the whole conversation — that memory is 'state'. REST is stateless by design: the server remembers nothing between requests, so every request is a fresh stranger at the counter. Therefore each request must carry proof of identity by itself (a token or API key in a header). Statelessness is why REST scales to millions of clients, and it is the single fact that explains the whole auth pattern.
What is the difference between authentication (authN) and authorization (authZ), and how do HTTP 401 and 403 map to them?	authN = 'who are you?' (proving identity, e.g. logging in). authZ = 'what are you allowed to do?' (permissions). 401 Unauthorized = authN failed: no token, bad token, or expired token ('I don't know who you are'). 403 Forbidden = authN succeeded but authZ failed ('I know exactly who you are, and you may NOT do this'). Interview one-liner: 401 is 'I don't know you'; 403 is 'I know you, and no.'
Compare an API key and an auth token: what does each identify, how long does each live, and why is a token considered more secure even though both can be stolen?	An API key identifies an APPLICATION and is long-lived (often never expires); the real secret rides on every request, so a leak = full access until a human revokes it (example: Meraki). An auth token identifies a USER via a login step (POST credentials -> token), is short-lived (e.g. Catalyst Center ~60 min), and your password is exposed only once — after that only a disposable token travels. Token is 'more secure' because of EXPIRY: a leaked token self-destructs (blast radius ~1 hour), and it can carry finer scope. Both must never be hardcoded or committed.
SCENARIO (CML_login.py): CML's login contract is POST {url}/api/v0/authenticate with body {"username":..., "password":...}. On success it returns 200 and the token as the WHOLE body (a bare JSON string), not {"token": ...}. After response = requests.post(login, json={...}, ...), how do you get the token, and what type is it?	token = response.json(). Because CML returns the token AS the entire body (a JSON string), response.json() here returns a Python str (the token itself), NOT a dict — so there is no ['token'] key to index. Always read the vendor doc for the exact response shape; do not assume {"token": ...}. (Contrast: many APIs DO wrap it in a dict.)
SCENARIO (CML_login.py): after login you wrote token = response.json() then print('token length', len(token)) instead of print(token). Why print the length and not the token itself?	The token is a live 279-char credential — anyone holding it is treated as you (Bearer). print(token) drops it into terminal scrollback, logs, and any screenshot you might paste, which leaks a working credential (violates AUTOCOR 3.6 / the no-secrets-in-output rule). print(len(token)) proves you captured a real token (a big number like 279) while leaking nothing. Habit reviewers and interviewers look for: never print/log a secret.
SCENARIO (CML_login.py): running against https://10.104.55.88 raised ssl.SSLCertVerificationError: CERTIFICATE_VERIFY_FAILED: self-signed certificate, before any credentials were sent. In plain terms, what failed and why?	The https URL triggers a TLS handshake that does TWO things: (a) set up encryption, and (b) AUTHENTICATE the server via its TLS certificate. Your OS trust store only trusts certs signed by known CAs. CML's cert is SELF-SIGNED (CML signed its own), so it is not in the trust store, so verification fails and requests refuses to continue — the POST body was never sent. The error is about server identity, not your password. Read the meaningful line (SSLCertVerificationError / self-signed), not the urllib3 stack.
What does verify=False actually turn off in requests, why is it dangerous, and what is the correct fix for CML's self-signed cert (AUTOCOR 3.5)?	verify=False disables ONLY the server-authentication check (b); encryption still happens. The danger: you can no longer tell whether you are talking to the real CML or a man-in-the-middle who could harvest the credentials you POST. Acceptable ONLY as a conscious, documented exception on a lab box you control — NEVER in production. Correct fix: trust CML's cert explicitly — export it to a .pem and pass verify='/path/to/ca.pem', keeping both encryption AND authentication. In prod, deploy a CA-signed certificate.
SCENARIO (CML_login.py): to list labs you sent requests.get(f'{url}/api/v0/labs', headers={'Authorization': f'Bearer {token}'}, timeout=10, verify=False). Why does the token go in a HEADER (not the URL or body), and what is the exact header format?	Identity is metadata about the request, which is what headers are for. Not the URL: URLs are logged everywhere, so a secret in a URL leaks into logs/history. Not the body: GETs have no meaningful body, and the body is for data, not identity. Format: header name Authorization, value 'Bearer <token>' (the word Bearer, one space, then the token). Bearer = 'whoever bears this token is treated as the user.' Omit the header and CML treats you as a stranger -> 401.
SCENARIO (CML_login.py): GET /api/v0/labs returned 200 and print(response.json()) showed ['d6495a1c-...', '0229552b-...', ...] (5 strings). What did .json() do, what is this data, and why might you need MORE calls to be useful?	The body always arrives as TEXT; .json() PARSES that JSON text into a Python object — here a JSON array became a Python list of 5 strings. (response.text would give the raw string; .json() gives data you can index/loop.) These strings are the 5 lab UUIDs — ids only, no title or state. CML's /labs returns just ids, so to get details you call GET /api/v0/labs/{id} PER id. 'List returns ids; detail needs a call per id' is a very common REST pattern (Catalyst Center behaves the same).
What is 'persistent auth' (AUTOCOR 1.6), and what are the reactive vs proactive strategies for handling token expiry?	Persistent auth = log in ONCE, keep the token on your client, and reuse it across many requests instead of logging in on every call (faster, and does not hammer the login endpoint). Handling expiry: REACTIVE (default) = use the token until a request returns 401, THEN log in again and retry that request — simple, and you never refresh a token that still has life. PROACTIVE = track issue time and renew shortly before the known limit (e.g. before 60 min). Reactive is common because a 401 is an unambiguous 'token is dead' signal.
