SCENARIO (cml_client.py): get_lab calls response.raise_for_status() before return response.json(). __main__ loops for lab_id in labs and calls get_lab with no try. One lab id is bad. What happens to the labs after it, and why?	raise_for_status() does nothing on 200 and raises requests.exceptions.HTTPError on 4xx/5xx. An uncaught exception stops the whole script, so the for loop never reaches the later ids. The later labs were fine; one bad call in front of them killed the run. Same failure as a Module 2 backup with no per-device try: one dead host aborts the rest. The try must sit inside the for, around one lab.
SCENARIO (cml_client.py): client.get_lab('this-lab-does-not-exist') raised HTTPError: 400 Bad Request for url .../api/v0/labs/this-lab-does-not-exist. Why 400 and not 404, and why was detail never created?	CML lab ids are UUIDs. 'this-lab-does-not-exist' is ordinary text, so CML rejects the shape of the request before it searches. 400 Bad Request means the request is malformed. 404 would mean the id is a valid UUID and no lab has it. get_lab raises on raise_for_status(), so return response.json() never runs and the name detail is never assigned. The id you sent and the dict CML would have returned are different values.
Why must print(detail['lab_title'], detail['state']) sit inside the try, on the line after detail = client.get_lab(lab_id), and not below the except?	detail only exists when get_lab returns. On HTTPError the return never happens, so detail was not assigned. A print below the except still runs after the error is caught, then raises NameError, which is not an HTTPError, so the script dies anyway. The print belongs in the try, immediately after a successful return. The except only reports the failure and lets the for continue.
SCENARIO (cml_client.py): the handler was written as if client.get_lab == 400 or 404. Why does that not test the HTTP status, and why is 'or 404' especially wrong?	client.get_lab is the method (the function), not the number CML sent. The status is error.response.status_code, because raise_for_status() attaches the response to the HTTPError. 'status == 400 or 404' is parsed as (status == 400) or (404). The bare number 404 is true, so the branch would run for every error, including 401. Write if status in (400, 404).
SCENARIO (cml_client.py __main__): inside except HTTPError, status 400 or 404 prints 'Invalid lab ID' and continues; status 401 calls client.login() and then get_lab(lab_id) once more inside a nested try. Why is 'skip the lab' the wrong reaction to 401?	401 means the token on the session is no longer accepted. CML is not judging the lab id; this request arrived as a stranger. Skipping drops a lab you are allowed to see. login() stores a new token and updates the session Authorization header. Then you retry that same lab_id once. If the second call is also 401, stop. Logging in forever is a loop. 400/404 will not be fixed by a new token, so those are the skip cases.
Why does the 401 retry need its own try/except instead of calling get_lab again as a bare line under client.login()?	The retry is another HTTP call. It can raise HTTPError too (still 401, or 404, or 500). A bare call would be uncaught and would stop the for loop, which is the bug this session fixed. The inner except prints 'not authorized still' and then the outer for moves on. One retry, then give up.
CML's POST /api/v0/authenticate returned 403 when the script sent the placeholder username 'your-cml-username'. How does that 403 differ from a 403 on GET /labs/{id} after a successful login?	On /authenticate, CML uses 403 to reject a bad username or password. That is a vendor exception to the textbook split (many APIs use 401 for bad credentials). The request never got a token. A 403 on a later GET, after login already returned 200, means the token is valid and this account is still not allowed to do that action. A new login with the same account will not fix it. Read the URL in the HTTPError: /authenticate versus /labs/{id} tells you which meaning you have.
What is the difference between an HTTPError (400/401/404) and requests.exceptions.ConnectTimeout when calling CML?	HTTPError means TCP connected and CML sent an HTTP status. You branch on that status. ConnectTimeout means nothing answered within timeout=10: wrong IP, VPN down, CML powered off. There is no status code, because there was no HTTP response. Catching only HTTPError does not catch a timeout. A timeout is a reachability problem, the same family as NetmikoTimeoutException in Module 2.
