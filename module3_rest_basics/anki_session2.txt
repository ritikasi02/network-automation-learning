SCENARIO (first_call.py): you have response from requests.get and user = response.json(). Why can you json.dump(user) but not json.dump(response)? Is response 'not Python'?	response IS a Python object (a requests.Response). json.dump only accepts JSON-legal types: dict, list, str, int, bool, None. A Response is a custom class, so dump raises TypeError: Object of type Response is not JSON serializable. .json() parses the BODY into a list/dict — that is what dump can write. Same family as dumping a set in Module 1.
SCENARIO (first_call.py): each API user dict has many keys (email, address, company, ...). The report file should only have id, name, city. What does 'build a new list of small dicts' mean, and why not dump user as-is?	Each entry is a FAT dict. You CREATE a smaller dict with {} (you are building): {'id': entry['id'], 'name': entry['name'], 'city': entry['address']['city']}. Start with an empty list BEFORE the loop, append each small dict, then dump that list AFTER the loop. Dumping user as-is works but keeps every field — a real compliance job keeps hostname/site/status, not the whole controller payload.
SCENARIO (first_call.py): deet = [] then inside the loop small = { ... } and deet.append(small). Why must the empty list be created BEFORE the for, and why must json.dump be AFTER the for?	If deet = [] were inside the loop, you would wipe the list every user and keep only the last one. If dump were inside the loop, you would overwrite the file 10 times (last write wins). Empty list once → append each pass → dump once when the list is complete. That four-step sentence (empty list, build small dict, append, dump after) is the 'project and save' pattern for APIs.
What is the difference between {} and [] when you write small = {'id': entry['id'], ...} versus entry['id']?	{} CREATES a new dict (you are packing a trimmed record). [] LOOKS UP a field on an existing dict (entry already came from the API). Both appear in the same block: read with [], write a new box with {}. entry{'id'} is invalid. append is a method: deet.append(small) with parentheses, not append{...}.
SCENARIO (first_call.py + labs.json): the users API body starts with [ so user is a list and for entry in user is correct. labs.json starts with { 'labs': [ ... ] }. After data = json.load(f), why is for lab in data wrong, and what do you loop instead?	data is a DICT whose one useful key is the string 'labs'. for lab in data loops the KEYS (just 'labs'), not the lab records. The list of labs is data['labs']. Then for lab in data['labs']: each lab is a dict with title and state. Rule: first character [ vs { decides the first lookup. Do not reuse the users loop on a new JSON just because both are JSON. Real APIs mix both shapes (Catalyst Center often wraps devices in {'response': [...]}).
SCENARIO (first_call.py): the engineer wrote data = {} and looped it, then later json.load(f) without assigning, then print(data) and saw {}. Why was the file 'not there'?	data = {} created an EMPTY dict in memory — not the file. The loop over {} runs zero times. json.load(f) RETURNS the parsed JSON; if you do not assign (data = json.load(f)), the value vanishes. print(data) still shows the empty {}. Order: load first (and catch the return), THEN loop. Same as user = response.json() before for entry in user.
SCENARIO (first_call.py): json.load(data, f) raised TypeError: load() takes 1 positional argument but 2 were given. json.load(data) then raised AttributeError: 'dict' object has no attribute 'read'. What does load vs dump each take?	json.load reads a FILE: one argument, the file object (json.load(f)). json.dump writes Python data to a file: two arguments (json.dump(deet, f)). Swapping them is the common mix-up. Passing a dict to load fails because a dict has no .read() — only the open file does. Pair to remember: load = file -> Python; dump = Python -> file.
SCENARIO (labs.json): three labs, states STARTED / STOPPED / STARTED. The working filter is for lab in data['labs']: if lab['state'] == 'STARTED': print(lab['title']). Why do you compare lab['state'] (not data['state']), and why is else: continue unnecessary?	Each lab is one dict in the list. state lives ON THAT DICT, so lab['state']. data['state'] would look for state on the OUTER wrapper (it is not there -> KeyError). else: continue does nothing extra — if the if is false, the for already moves to the next lab. The if alone is the filter. Real-world: only show labs that are up, or only interfaces with status down.
