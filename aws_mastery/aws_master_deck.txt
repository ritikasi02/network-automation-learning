SCENARIO: a teammate creates an S3 bucket and leaves it readable by anyone on the internet. Config backups land in it. They say AWS is responsible for security, so the public bucket is Amazon's fault. Which side of the shared responsibility model failed, and what has to change?	The customer side failed. AWS runs the storage service. The bucket's access setting is the customer's configuration, the same class of mistake as giving a machine more privileges than its job. Change the bucket so it is not public, and give each workload only the actions it needs. AWS secures the platform. You secure identity, network rules, and data.
You sign up with GitHub on Sign up for AWS (new). The console home URL contains region=ap-southeast-2. The Budgets page URL contains us-east-1. Which region will a later Lambda actually be created in, and why are both URLs telling the truth?	The Lambda is created in ap-southeast-2 (Asia Pacific, Sydney). India on this signup is assigned Sydney, and this signup cannot move the project to N. Virginia. The Budgets console is hosted in us-east-1 because a budget watches money for the whole account. It is not a resource that lives in Virginia. Stay in Sydney for every Lambda and bucket.
The account is on the free plan with $100 credits and about 183 days left. A monthly cost budget named My Monthly Cost Budget is set to $10 and shows $0 used. Does that budget stop a resource from running, and what else do you watch so the account does not end early?	The budget only emails you. It does not stop the resource. On the free plan, credits cover usage, so the amount owed can stay $0 while credits shrink. Watch Credits remaining and days remaining. The plan ends when the credits run out or the trial days end, whichever comes first, and then the account closes unless you upgrade.
SCENARIO: the Mac already has a default AWS profile with region ap-south-1. For the new project you run aws login --profile hello-aws and set that profile's region to ap-southeast-2. Why is the named profile required, and why do you not run aws configure and paste an AKIA access key?	Without --profile hello-aws, the CLI uses default and talks to Mumbai, which is not this project. hello-aws is the Sydney session. aws login opens a browser, you approve the GitHub login, and the CLI keeps a temporary session for about 12 hours. An AKIA key is a long-lived secret, the same kind of leak as a Meraki API key in git. This signup's owner is the GitHub login. Do not create a second user or a key pair for the lab.
sts get-caller-identity --profile hello-aws prints an Arn whose middle looks like assumed-role/AccountFullAccessRole/SESSION. What did you assume, and why is that acceptable for an empty lab but the wrong identity for a Lambda that only needs one bucket?	You assumed the role AccountFullAccessRole for this session. The role name is the policy: full access to the project, the cloud version of permit ip any any. Fine while you are the human setting up an empty lab. A Lambda must not run as that role. When a function needs S3, it gets its own role that allows only that bucket. Your login is the person. The function's role is the program.
SCENARIO (lab-hello, AWS Lambda console): the starter code is "def lambda_handler(event, context): return {'statusCode': 200, 'body': json.dumps('Hello from Lambda!')}". You press Test with the event {"file": "beach.jpg"}. The body still says Hello from Lambda, not beach.jpg. Your S3 bucket holds a PDF, no image. Did the function read your file or your event, and why is beach.jpg irrelevant here?	Neither your file nor your event was used. Test only hands the typed JSON to the function as "event" and shows what it returns; S3 is never contacted. The starter code never reads event, so it returns the same fixed string no matter what you type. beach.jpg was a made-up label on a pretend doorbell, not a filename AWS looks up. The PDF in S3 is unrelated because this function does not touch S3.
What is AWS Lambda in one sentence, and name two jobs it is wrong for?	Lambda is a function AWS runs when an event arrives, then stops; you are billed only for the seconds it runs, and you never patch a server. It is wrong for a program that must stay up continuously (use a long-running server / EC2) and for work longer than its 15-minute limit. "Cold start" is the slower first run after idle while AWS builds the environment; it is not a code bug.
SCENARIO (lab-hello): the code does "body: json.dumps(event['file'])" and you send the event {"name": "beach.jpg"}. The Response panel turns red with errorType KeyError, errorMessage 'file', and no statusCode anywhere. You expected statusCode 200 regardless. Why is there no 200?	A return is one statement: Python must finish building the whole dict before returning it. Building it evaluates event['file'], which raises KeyError because there is no 'file' key, so the return never completes and no statusCode is ever produced. The run is marked failed because the function raised, not because of any number. On a plain Test or event trigger, AWS does not read statusCode at all; success means the function returned, failure means it raised.
SCENARIO (lab-hello): a missing key crashed the function. You must decide between returning a 400 that says the key is missing, or defaulting the filename to a placeholder like "unknown.jpg" so the function keeps going. Which is correct and why?	Return the 400. Defaulting to a made-up value lets the function keep working on data that is not real, so in a live app it would resize, email, or report the wrong thing while reporting success and hiding the problem. A 400 fails loud and early and tells the caller to fix their request. Rule: validate input at the door, fail clearly, never substitute a fake value to avoid an error. Read the key with event.get('file') (returns None instead of raising) so you choose what happens, not Python.
SCENARIO (lab-hello): line 4 is "filename: event.get('name')" (a colon). Running it gives UnboundLocalError: cannot access local variable 'filename', pointing at line 5 "if filename is None:". What is wrong and what is the fix?	A colon makes "filename: ..." a type annotation, not an assignment, so filename is never given a value and line 5 cannot read it. The fix is the assignment operator "=": filename = event.get('name'). Lesson: the traceback names the exact variable and line, so read it top-down, then look there. UnboundLocalError means "this local name was never assigned", different from KeyError (a dict key is missing).
Why put print(json.dumps(event)) as the FIRST line of a Lambda handler, and what happens if it is placed after the return?	First-line logging captures the input before any logic that might crash or return early, so even if the function blows up later you can see what came in. A print placed after a return is dead code: return exits the function immediately, so it never runs (this looks exactly like "no print line appears in the log"). Rule of thumb: log the input at the top, log the result just before each return, because the CloudWatch log is the only witness to a run no human watched.
SCENARIO: lab-hello works on the Test button but you want a browser to call it. You turn on a Function URL with Auth type NONE. What did that create, and what is the security caveat?	A Function URL is a dedicated public HTTPS address bound to that one function; hitting it invokes the function, with the HTTP request delivered as the event. Auth type NONE means anyone on the internet with the URL can invoke it. That is acceptable only because this function just echoes a filename and touches nothing. Never use NONE for a function that reads data or spends money. Function URLs suit "one function, one URL"; API Gateway is the choice for a full API (routing, auth, rate limiting, custom domain).
SCENARIO (lab-hello Function URL): you load the URL with no query string. The browser shows your 400 "file does not exist", not an error page, and the HTTP status really is 400. Is a 400 the same as "the page failed to load", and who chose that 400?	No. The page loaded fine; the exchange succeeded. The status is a separate verdict the server chooses and the browser only reads. Your function ran successfully and deliberately returned 400 to say "bad request". If the function had instead crashed (raised), your code would set no status and AWS's front door would return 502/500 on its own. A status is always chosen by whoever answered; the browser never invents it. With a Function URL, AWS reads your statusCode and makes it the real HTTP status, so now your 200/400 finally mean something to a caller.
SCENARIO (lab-hello Function URL): code reads event.get('name') and the browser request ...on.aws/?name=beach.jpg still returns 400. The logged event has top-level keys version, routeKey, rawPath, rawQueryString, headers, queryStringParameters, requestContext, isBase64Encoded, and "queryStringParameters": {"name": "beach.jpg"}. Where is the code looking vs where the value is?	event.get('name') searches only the top-level keys (the outermost keys of the event dict). There is no 'name' at that level, so it returns None and you get the 400. The value lives one level down, inside the queryStringParameters drawer: event['queryStringParameters']['name']. Lesson: the event shape is set by the trigger. A Function URL (payload v2.0) nests query params under queryStringParameters; a Test event you type by hand puts keys wherever you typed them; an S3 trigger nests the key at event['Records'][0]['s3']['object']['key']. Read the shape your actual trigger sends.
SCENARIO (lab-hello): to read a Function URL query param safely the code is "params = event.get('queryStringParameters'); if params is None: params = {}; filename = params.get('name')". Why guard params against None instead of writing event['queryStringParameters']['name'] in one line?	When the URL has no query string, AWS sends queryStringParameters as null (Python None), and reading a key off None raises a crash just like the earlier KeyError. The one-line chained lookup crashes if either level is missing. Reading each level with .get plus the None->{} guard turns "no query string" into your clean 400 instead of a traceback. 'params' is just a chosen variable name holding the drawer; the string passed to event.get is the real top-level key "queryStringParameters".
SCENARIO (lab-hello): the handler ends with "if filename is None: return {400...} return {200...}" where BOTH returns are indented inside the if. ?name=beach.jpg returns null; the plain URL returns 400. Why null, and what is the fix?	Both returns are inside the if block. When name is present, filename is not None, so the whole if is skipped, there is no return after it, and a Python function that ends without returning gives back None -> shown as null. The 200 return is also dead code: it sits right after return 400 in the same block and can never be reached. Fix: dedent the 200 return so it aligns with "if", making it a sibling of the if that runs when the if did not. In Python, indentation IS the block structure.
SCENARIO (module3_5_aws_taster/bucket.yaml): the file declares "ReportsBucket:" with "Type: AWS::S3::Bucket" and "BucketName: ritika-s3bucket-20262026". You run "aws cloudformation deploy --template-file bucket.yaml --stack-name hello-aws-bucket --profile hello-aws" and a real bucket appears. In this one command, what is the TEMPLATE and what is the STACK, and how do they differ?	The TEMPLATE (bucket.yaml) is a declarative wish-list: text that says what should exist, with no live state of its own. The STACK (hello-aws-bucket) is the live thing AWS creates and remembers: the set of real resources plus the state record of what it currently owns. MENTAL MODEL: template = the blueprint you hand over; stack = the built house AWS tracks. You can run the same template a thousand times; there is still one stack. WHY IT MATTERS: because the stack remembers state, CloudFormation can compare "what you want" (template) against "what exists" (stack) and compute only the difference, which is the whole point of declarative IaC. Worked example: edit the template and redeploy -> CloudFormation diffs template vs stack and changes only what moved.
SCENARIO (bucket.yaml): the resource block starts "ReportsBucket:" then "Type: AWS::S3::Bucket" then "BucketName: ritika-s3bucket-20262026". Three different "names" are in play. What is the logical ID, the physical name, and the Type, and who decides each?	LOGICAL ID = "ReportsBucket": a nickname YOU pick, used only inside this template/stack to refer to the resource; rename it freely, AWS does not care. PHYSICAL NAME = "ritika-s3bucket-20262026": the real-world name of the actual bucket, which must obey S3's global rules (unique, lowercase). TYPE = "AWS::S3::Bucket": AWS's fixed vocabulary from the resource schema; you cannot invent it, it tells CloudFormation which service and resource kind to build. MENTAL MODEL: logical ID is your label on the blueprint, physical name is the address of the built thing, Type is the catalog part-number. WHY: mixing these up is why beginners think "BucketName" is special Python; it is not, it is a Property defined by the AWS::S3::Bucket schema.
SCENARIO: you ask why "BucketName" and "PublicAccessBlockConfiguration" look like special keywords in bucket.yaml and wonder if they come from a Python library. Where do these words actually come from?	They come from the AWS resource SCHEMA for the Type you chose (AWS::S3::Bucket), not from Python and not invented by you. Each AWS resource type publishes a fixed list of allowed Properties with exact spellings; "BucketName" and "PublicAccessBlockConfiguration" are two of S3's. MENTAL MODEL: picking a Type is like picking a form; the Type dictates which fields (Properties) exist and how they are spelled. WHY: this is why a typo like "Buckitname" is rejected and why you cannot add a property S3 does not define. You discover valid properties from the AWS CloudFormation resource reference for that Type, the same way you read a library's API docs before calling it.
SCENARIO: bucket.yaml never mentions a region, yet the bucket was created in Sydney (ap-southeast-2). You deployed with "--profile hello-aws". Where did the region come from?	From the CLI PROFILE (hello-aws), not the template. The profile in ~/.aws/config holds "region = ap-southeast-2", so every API call the deploy makes is aimed at Sydney. MENTAL MODEL: the template says WHAT to build; the profile says WHERE to send the request and WHO is asking. WHY KEEP REGION OUT OF THE TEMPLATE: the same template can then be deployed to any region just by switching profile/region, which is what makes IaC portable. If you had deployed with a profile set to us-east-1, the identical template would have built the bucket in Virginia instead.
SCENARIO (bucket.yaml): you deploy once and get CREATE_COMPLETE with a new bucket. You change nothing and run the exact same "aws cloudformation deploy" again. It prints "No changes to deploy" and does nothing. Why, and what property of IaC is this?	CloudFormation diffs the template against the stack's remembered state; they are identical, so the change set (plan) is empty and there is nothing to execute. This is IDEMPOTENCY: describing a desired end-state means re-running when you are already in that state is a safe no-op. MENTAL MODEL: declarative = "make it look like this"; if it already looks like this, do nothing. CONTRAST: an imperative script like "aws s3 mb" would error "bucket already exists" on the second run because it blindly repeats an action. Terraform shows the same behaviour ("No changes. Your infrastructure matches the configuration"), which is why CloudFormation and Terraform are the same category of tool.
SCENARIO (bucket.yaml): under the bucket you add "Tags:" with "- Key: aws-project" and "Value: hello-aws", then redeploy. The events show ReportsBucket UPDATE_COMPLETE on the SAME bucket (not a new one). What is a Key/Value tag for, and why did this change happen in place?	A tag is a Key/Value label you attach to a resource; purposes are organization/search, cost allocation (group the bill by tag), access control (policies can key off tags), and automation (scripts find resources by tag). It changed IN PLACE because a tag is a mutable property: S3 can edit the label on the existing bucket without rebuilding it, so the physical bucket is untouched and you see UPDATE_COMPLETE, same resource. MENTAL MODEL: some properties can be edited live (tags), others cannot (the name). This distinction decides whether an update is harmless or a full replacement.
SCENARIO (bucket.yaml): you deliberately change BucketName to have a capital letter ("Ritika-s3bucket-20262026") and deploy. A red banner says "The resource ReportsBucket is in a UPDATE_FAILED state ... Bucket name should not contain uppercase characters." Before redeploying, predict: did CloudFormation validate the name up front, and what will happen to your original lowercase bucket?	It did NOT validate up front; the error came from S3 only when CloudFormation tried to make the change. Because BucketName is an IMMUTABLE property, changing it forces a REPLACEMENT: CloudFormation tries to CREATE a new bucket (the uppercase one) and only then delete the old one. S3 rejects the uppercase create -> UPDATE_FAILED -> automatic UPDATE_ROLLBACK -> stack returns to its last good state. Your original lowercase bucket SURVIVES untouched, because replacement is create-new-then-delete-old and the new one never succeeded. LESSON: always check whether a change is "in place" or "replacement" before deploying to something holding real data.
SCENARIO (uppercase-name rollback): the events show, during UPDATE_ROLLBACK_COMPLETE_CLEANUP, "ReportsBucket DELETE_IN_PROGRESS" then "DELETE_COMPLETE". You panic that your good bucket is being deleted. What is actually being deleted, and why is your data safe?	The FAILED REPLACEMENT attempt is being discarded, not your original. Replacement means create-new-then-delete-old; the new (uppercase) bucket was rejected by S3 so it was never really created, and during rollback CloudFormation cleans up that doomed replacement reference. Your original lowercase bucket "ritika-s3bucket-20262026" was never touched throughout, which is exactly why replacement does the new one first and only deletes the old after the new succeeds. LESSON (AUTOCOR 3.3): read stack events bottom-to-top; a DELETE during a ROLLBACK is almost always cleanup of the thing that just failed, not your working resource.
SCENARIO: after a failed uppercase deploy, you edit BucketName back to the lowercase "ritika-s3bucket-20262026" and redeploy to recover. You see "No changes to deploy" rather than UPDATE_COMPLETE. Is that a problem?	No, it is the expected and correct result. The rollback already reverted the stack's remembered state to the lowercase name, so when you put the template back to lowercase, template and stack are identical again and the change set is empty -> "No changes to deploy". MENTAL MODEL: recovery here was automatic (rollback did it); your edit just re-syncs the file with reality. If instead it had said UPDATE_COMPLETE, that would mean the stack had drifted from lowercase and needed fixing. Empty plan = already healthy.
SCENARIO: your bucket was created by the hello-aws-bucket stack. A teammate suggests deleting it directly in the S3 console. You instead run "aws cloudformation delete-stack --stack-name hello-aws-bucket --profile hello-aws". Why delete through the stack, and what would hand-deleting cause?	Delete through the stack so the source of truth and the real world stay in sync: delete-stack walks the stack's resource list, deletes the real bucket, then removes its own state record, leaving nothing orphaned. Hand-deleting in the console causes DRIFT: the stack still "believes" it owns a bucket that no longer exists, so later operations reason from a false picture and a future delete-stack tries to remove something already gone. RULE OF THUMB: whatever created a resource should be the thing that changes or destroys it (same discipline as "terraform destroy", never delete cloud resources by hand). NOTE: delete-stack succeeds only if the bucket is empty; a bucket with objects throws DELETE_FAILED.
SCENARIO: an interviewer asks "is CloudFormation basically Terraform?" You used CloudFormation this session (YAML template, stack holds state, aws cloudformation deploy). How are they the same and different, and how is a stack NOT like Git?	SAME CATEGORY: both are declarative, state-driven IaC; you describe desired end-state, the tool diffs against remembered state and changes only the difference, and both are idempotent. DIFFERENT: CloudFormation is AWS-only, AWS manages the state for you inside the stack, templates are YAML/JSON. Terraform is multi-cloud, YOU manage the state file (terraform.tfstate), language is HCL. NOT LIKE GIT: a stack is not a history of text versions you can diff/revert commit-by-commit; it is a live record of real resources and their current state. Git versions your template FILE; the stack manages the actual bucket. You still keep bucket.yaml in Git for history AND let CloudFormation manage the live resource; they do different jobs.
