What is SSH automation, in one mental model, and why does that model explain both its usefulness and its fragility?	SSH automation is a robot typing at a human terminal and reading the text that scrolls back. Usefulness: it does the same keystrokes an engineer already knows (ssh, show running-config, save the output) across hundreds of devices on a schedule. Fragility: the program is scraping a human interface — prompts, paging (--More--), banners, formatting — so a CLI change, unexpected [confirm], or custom prompt can break the script. That is why the industry is moving to APIs (REST, NETCONF/RESTCONF): those are machine interfaces with structured data and no prompt.
How does Netmiko know a command like show running-config has finished, and what goes wrong if it guessed with a fixed sleep instead?	Netmiko learns the device's base prompt after login (e.g. CAT9k_AO#) and, after sending a command, keeps reading until that prompt reappears. That means 'the device is idle and waiting for the next command.' A fixed sleep is wrong both ways: too short and you capture partial output; too long and you waste time or still miss a hung [confirm] prompt. Netmiko also sends terminal length 0 to disable --More-- paging so a pager prompt never interrupts the stream.
What is the difference between Paramiko and Netmiko, and when would you use each?	Paramiko is the low-level Python SSH library: a raw encrypted channel that sends and receives bytes. It knows nothing about Cisco prompts, enable mode, or paging. Netmiko is built on top of Paramiko for network devices: it detects the prompt, disables paging, handles enable/config mode, and uses a device_type (cisco_ios, cisco_xe, ...) so you do not re-implement terminal handling. Use Netmiko for network gear; use Paramiko only if you need raw SSH to a general Linux host.
SCENARIO (backup_configs.py): credentials are read with username = os.environ['NET_USER'] and password = os.environ['NET_PASS'], after the engineer ran export NET_USER=... and export NET_PASS=... in the same terminal. Where do those values actually live, and why is that better than putting them in the .py file or in devices.yaml?	They live in the SHELL'S MEMORY — the environment table of that terminal session. When python3 starts, it inherits a copy of that table, and os.environ looks the names up. They are not on disk in this project and are gone when the terminal closes. Better than the .py file because source code gets committed to git (treated as public). Better than devices.yaml because inventory answers 'which devices' and credentials answer 'who is allowed in' — mixing them is how passwords leak when someone commits the inventory. Production upgrade: same os.environ interface, values injected by a secrets manager.
SCENARIO (backup_configs.py): the script does with ConnectHandler(**device) as conn: instead of conn = ConnectHandler(**device). What does **device do, and why does the with matter in a real backup job?	** unpacks the dict into keyword arguments, so ConnectHandler(**device) is the same as ConnectHandler(device_type=..., host=..., username=..., password=...). The with is a context manager: it disconnects the SSH session when the block ends, EVEN IF an exception is raised inside. Without it you must remember conn.disconnect(); if an error fires first, the session leaks and the device keeps a VTY line occupied. Same safety as with open(...) auto-closing a file.
SCENARIO (devices.yaml): the file starts with a top-level key devices: then a YAML list of host/device_type entries. After inventory = yaml.safe_load(f), why is the loop written for entry in inventory['devices'] (quoted string), not inventory[devices], and what is each entry?	yaml.safe_load turns the file into a Python dict whose one top-level key is the string 'devices'; the value of that key is a LIST of device dicts. inventory['devices'] looks up that list. Bare inventory[devices] looks for a Python VARIABLE named devices, which was never defined, so you get NameError. Each entry is one device dict, so entry['host'] and entry['device_type'] work. Rule: a name that lives inside a dict or YAML file is looked up with a quoted string.
Why must the ConnectHandler / backup / write-file block be indented UNDER the for entry in inventory['devices'] loop, not after it?	Indentation is Python's 'once per item' signal. Inside the loop, connect-backup-save runs for EVERY inventory entry. Outside the loop, the for only builds the last device dict, then you connect once — so with two devices you would only back up the last one. Real-world: adding a 50th router should be a YAML line, not a copy-paste of connect code; the loop is what makes that true.
Why use yaml.safe_load and not yaml.load when reading devices.yaml?	yaml.load can construct arbitrary Python objects from the file, which is a remote-code-execution hole if the YAML is ever untrusted or edited by someone else. yaml.safe_load only builds plain data — dicts, lists, strings, numbers. Always safe_load for inventory files. (This is the same class of rule as 'never pickle untrusted data.')
SCENARIO (backup_configs.py): hostname = conn.find_prompt().strip('#>'). What does find_prompt return, what does strip('#>') actually do (it is NOT 'delete the substring'), and why is scraping the prompt a fragile way to learn the device name?	find_prompt() sends a newline and reads back the CLI prompt, e.g. CAT9k_AO# (# = enable, > = user exec). strip('#>') treats its argument as a SET of characters to trim from both ends, so it removes a trailing # or > and leaves CAT9k_AO — it does NOT delete the literal string '#>'. Fragility: a custom prompt or config-mode prompt like CAT9k_AO(config)# leaves junk in the filename. An API would return a structured field {'hostname': 'CAT9k_AO'} with no guessing. That contrast is why SSH scraping is being replaced.
SCENARIO (backup_configs.py): ts = datetime.now().strftime('%Y%m%d-%H%M%S') and path = os.path.join('backups', f'{hostname}_{ts}.cfg'). Why this timestamp format, and why os.path.join instead of 'backups/' + name?	strftime renders the datetime object into a string using format codes (%Y year, %m month, %d day, %H hour, %M minute, %S second), e.g. 20260903-154725. That format is sortable (alphabetical order = time order) and filename-safe (no spaces or colons). os.path.join uses the correct separator for the OS (/ on Mac/Linux, \\ on Windows) so the same script works on a laptop and a Linux CI runner. Real-world: nightly backups must not overwrite last night's file — the timestamp is how you find 'the config as of last Tuesday' after a bad change.
SCENARIO (backup_configs.py + devices.yaml): the inventory has a good sandbox host and a dummy host with a typo (devnetsandboxiosxec9.cisco.com). The run printed a success line for CAT9k_AO, then TIMEOUT: cannot reach <dummy>. Why wrap try/except AROUND each device (not the whole script), and how do you tell TIMEOUT from AUTH FAIL?	If try wrapped the whole script, one dead device would abort the process and every later device would be skipped — in a 200-router nightly job that is worse than missing one box. Per-device try means: log the failure, continue the loop. NetmikoTimeoutException = cannot reach the device (wrong IP/DNS, down, port 22 blocked) — a NETWORK/reachability problem. NetmikoAuthenticationException = TCP/SSH reached the device but username/password were rejected — a CREDENTIALS problem. Timeout vs auth is the first split on an SSH automation ticket.
Why is SSH/CLI scraping being replaced by APIs (REST, NETCONF/RESTCONF), and what one sentence should you say in an interview?	CLI output is unstructured text designed for human eyes: parsers (regex/TextFSM) break when formatting changes; there is no real idempotency; prompts and paging are fragile; failures are hard to detect (did the command apply?). APIs return structured JSON/XML, have status codes, and (for NETCONF/YANG) a formal data model. Interview one-liner: SSH automation scrapes a human interface; APIs consume a machine interface. Scraping is fragile because CLI output was designed for people, not programs.
